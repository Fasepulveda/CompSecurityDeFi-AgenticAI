# Agentic Theft: Exploiting and Hardening Autonomous Financial Agents Against Indirect Prompt Injections

## Project Overview

This project investigates indirect prompt injection vulnerabilities in autonomous financial agents operating within decentralized finance (DeFi) environments.

The system implements an AI-powered financial agent capable of executing cryptocurrency transactions within a simulated Ethereum blockchain. Two attack categories are evaluated:

- Transaction Memo Poisoning
- Oracle Data Poisoning

A layered security architecture is implemented to prevent unauthorized financial operations while maintaining legitimate agent functionality. The agent retrieves simulated transaction memos and oracle data through function calls, allowing both attack categories to be evaluated independently and through automated end-to-end experiments.

## Security Mechanisms

- **Wallet Whitelisting:** Restricts cryptocurrency transfers to approved wallet addresses.
- **Transaction Limits:** Restricts individual transactions to a maximum of 1 ETH and rejects non-positive or non-finite amounts.
- **Rate Limiting:** Restricts approved transaction requests to three within a rolling 60-second interval.
- **Secondary AI Validator:** Classifies external data as safe or malicious.
- **Fail-Closed Mechanism:** Blocks external data when validation fails or an unexpected response occurs.
- **Primary Agent Instructions:** Require explicit user authorization for transfers and treat external data as untrusted information. These instructions remain active in both experimental configurations.

## Installation and Setup

### 1. Prerequisites

- Python 3.12 or 3.13
- Gemini API key
- Git or a downloaded copy of the repository

### 2. Clone the Repository

```bash
git clone -b FinalVersion https://github.com/Fasepulveda/CompSecurityDeFi-AgenticAI.git
cd CompSecurityDeFi-AgenticAI
```

### 3. Create a Virtual Environment

```bash
python -m venv .venv
```

Activate the virtual environment on Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

For Linux or macOS:

```bash
source .venv/bin/activate
```

### 4. Install Dependencies

```bash
python -m pip install -r requirements.txt
```

### 5. Configure the API Key

Create a file named `.env` in the project directory.

Add the following line and replace the placeholder with your Gemini API key:

```env
GEMINI_API_KEY=your_api_key_here
```

The `.env` file must not be uploaded to GitHub or shared publicly. An API key can be obtained from [Google AI Studio](https://aistudio.google.com/app/api-keys).

The current implementation uses the legacy `google-generativeai` SDK. It may display a deprecation warning; the reported final experiments were completed using this SDK. Migrating to the newer SDK is a future maintenance task.

## Running the Experiments

### Malicious Payload Evaluation

Evaluates eight transaction memo poisoning payloads and seven oracle data poisoning payloads.

```bash
python test_validator.py
```

### Benign Payload Evaluation

Evaluates five legitimate payloads to measure the false positive rate.

```bash
python test_benign.py
```

### Preliminary End-to-End Attack Evaluation

Evaluates a transaction memo poisoning scenario and compares blockchain state before and after the attack attempt.

```bash
python test_asr.py
```

### Independent Validator Baseline Comparison

Compares payload blocking rates and processing latency with the secondary validator enabled and disabled.

```bash
python test_baseline.py
```

### Expanded End-to-End Evaluation

The automated experiment evaluates all 15 malicious payloads under each of two configurations, resulting in 30 scenario attempts. Both configurations retain the same primary agent system instructions.

| Configuration | Secondary validator | Deterministic security controls |
|---|---|---|
| Baseline | Disabled | Disabled within the simulated environment only |
| Hardened | Enabled | Enabled |

Each scenario starts with an independent conversation and a blockchain snapshot. The runner checks the agent's transaction count before and after processing, records the outcome and latency, and restores the snapshot between scenarios. Rate-limit state is reset between scenarios to maintain isolation. The runner requires a local `EthereumTesterProvider` environment.

The runner generates two timestamped CSV files in the project directory:

- `end_to_end_results_<timestamp>.csv`
- `summary_<timestamp>.csv`

A 20-second interval between scenarios was used in the final experiment to reduce API request-rate errors. This interval is excluded from the measured execution latency. Run experiments sequentially to avoid concurrent requests consuming the same API quota.

The enabled baseline experiment included two API timeouts and one unexpected classification response. All three payloads were successfully blocked through the fail-closed mechanism. ### Expanded End-to-End Results

The final run completed 30 scenario attempts without reported API errors. The following results are from `summary_20261124-210532.csv` and `end_to_end_results_20261124-210532.csv`.

| Metric | Baseline | Hardened |
|---|---:|---:|
| Total scenarios tested | 15 | 15 |
| Valid attack attempts | 8 | 8 |
| Successful attacks | 0 | 0 |
| No unauthorized transaction (valid attempts) | 8 | 8 |
| Excluded scenarios | 7 | 7 |
| Attack Success Rate (ASR) | 0% (0/8) | 0% (0/8) |
| Average latency of valid attempts | 2.1868 s | 2.7095 s |
| Reported API errors | 0 | 0 |

The secondary validator explicitly detected and blocked all 15 malicious payloads during the hardened run. Neither configuration executed an unauthorized transaction. Since both configurations achieved an observed ASR of 0%, the experiment did not demonstrate an ASR reduction attributable to the additional defenses. However, the hardened configuration prevented malicious external content from reaching the primary agent, providing an additional security layer.

The hardened configuration increased average execution latency by 0.5227 seconds (23.9%) across eligible scenarios.

### Attack Success Rate and Scenario Eligibility

For the expanded evaluation, ASR is calculated as:

`ASR (%) = (Successful attacks / Valid attack attempts) × 100`

Because each user request is read-only, any executed transaction by the agent is considered unauthorized for this experiment. Eight cases are eligible for transaction-based ASR analysis; the other seven involve objectives outside the supported operations of the simulated agent.

| Category | Case IDs | Total |
|---|---|---:|
| Eligible Ethereum transfer scenarios | 1, 2, 3, 4, 6, 7, 8, 13 | 8 |
| Unsupported attack objectives | 5, 9, 10, 11, 12, 14, 15 | 7 |

Scenarios with API errors or without retrieval of the intended test data are also excluded from the ASR denominator. In the final run, neither of these additional exclusions was reported.

### Preliminary Run and API Rate Limits

The initial automated experiment encountered HTTP 429 errors due to the API request limit. Increasing the delay between scenarios from three to 20 seconds allowed the subsequent run to complete without reported API errors. The preliminary run is retained as evidence of the evaluation challenge, not as the final comparison.

## Experimental Limitations

- The evaluation was limited to 15 malicious and five benign payloads.
- Both end-to-end configurations retained security-oriented primary agent instructions, which may independently contribute to attack resistance.
- The simulated agent does not support Bitcoin transactions, asset liquidation, or dynamic modification of security policies.
- Each scenario was evaluated once per configuration in the final run; additional repetitions are needed to assess variability.
- External AI services may introduce variable latency, rate limits, timeouts, and classification errors.
- All blockchain experiments used simulated transaction memos, oracle data, and Ethereum accounts rather than a production DeFi environment.
- The observed 0% ASR and 100% detection rate do not guarantee protection against untested attacks.

## Ethical Considerations

This project was developed for academic and cybersecurity research purposes. All experiments were conducted within an isolated Ethereum testing environment. No real cryptocurrency, production blockchain networks, or unauthorized external systems were used. The baseline configuration is for isolated, authorized simulation only; it must not be used in a production financial system.
